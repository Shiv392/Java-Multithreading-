⭐⭐⭐ **Visibility Problem** →

In a multithreaded application, each thread may work with its own **local copy/cache of data** for performance.

If multiple threads are sharing the same object/variable and:
* One thread **changes** the value
* Another thread **reads** the same value

then the reading thread is **not guaranteed to immediately see the latest value** written by the other thread.
This is called the **Visibility Problem**.

Example →
boolean flag = false;

Thread 1 → reads/writes flag
Thread 2 → reads flag

Suppose:

Initial:
flag = false

Thread 1:
flag = true

Thread 2: Thread 2 may continue reading its previously cached/stale value:
Thread 2 → false

instead of seeing:
Thread 2 → true

This lack of guaranteed visibility between threads is called the **Visibility Problem**.


⭐⭐⭐ Solution → `volatile` keyword

Use the `volatile` keyword when a variable needs **visibility across threads**.
private volatile boolean flag = false;

volatile` provides a **visibility guarantee**: when one thread writes a new value to a volatile variable, other threads' subsequent reads are guaranteed to see that updated value.

What `volatile` solves →
Thread 1
   |
   | writes new value
   ↓
volatile variable
   |
   ↓
Other threads can see the updated value

So, `volatile` solves the **visibility problem**.

⭐ Important →
`volatile` **does NOT provide atomicity**.

Example:
volatile int count = 0;

count++;
count++ is not atomic because it involves:

read → modify → write

So multiple threads can still cause a **race condition**.

⭐ One-Line Interview Definition →
Volatile guarantees visibility of changes to a variable across threads, but it does not guarantee atomicity.
